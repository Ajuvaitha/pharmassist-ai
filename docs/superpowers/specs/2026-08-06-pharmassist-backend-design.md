# Pharmassist Backend — Design Spec

**Date:** 2026-08-06
**Status:** Approved, ready for implementation planning
**Scope:** A production-foundation backend for `frontend/`, plus the frontend rewiring needed to consume it.

---

## 1. Problem

`frontend/` is a complete 11-page React UI with no backend. Every page is fake in a different way:

| Page | How it fakes state |
|---|---|
| `App.tsx` | `patients` in `useState`, seeded from `data.ts`. Add/edit/stop prescription mutate memory. |
| `WardSweepPage` | Dispense stored in a local `patientState` map, wiped when the ward tab changes. |
| `BillingPage` | Reads the static `TRANSACTIONS` array; "Confirm Bill" sets a local map. |
| `InventoryPage` | Restock writes to a local `stocks` override map. |
| `RecentActivityPage` | `ALL_ACTIVITY` hardcoded inside the component. |
| `DashboardPage` | Imports `WARDS` / `INVENTORY` / `TRANSACTIONS` directly. |
| `LoginPage` | Ignores the password; the user picks their own role. |

Two consequences beyond "no persistence":

1. **The core domain loop does not exist.** Dispensing never creates a billing line and never moves stock. The three pages that should form one workflow are three unrelated mock datasets.
2. **Ward identity is string-matched.** Patients store `ward: 'Ward 4A'`; `WARDS` stores `'Ward 4A — General Medicine'`. The UI reconciles them with `.split(' — ')[0]`. This breaks on any ward name containing an em-dash.

This spec covers `frontend/` only. `demo/` (whiteboard/OCR) and `healthy-hands-app-main/` (separate TanStack app) are out of scope.

### Source of truth

The API is derived from **what the frontend code actually needs**, not from the pre-existing `API_ENDPOINTS_DETAILED.md` / `INPATIENT_AUTO_INDENT_MODULE_SPEC.md`. Those documents are treated as aspirational and will be **rewritten from the shipped code in Phase 6**. Their error-code vocabulary is reused where it fits.

---

## 2. Decisions

| Decision | Choice | Why |
|---|---|---|
| Target UI | `frontend/` | Cleanest of the three UIs; no whiteboard/OCR baggage. |
| Ambition | Real product foundation | Persistent DB, real auth, migrations, tests, deployable. |
| Stack | Node + TypeScript, Fastify, Prisma, Postgres | Repo is already TS/pnpm; a shared types package eliminates model drift by construction. |
| Auth | Seeded users, hashed passwords, JWT | Role and ward come from the DB record, not the login form. |
| Sweep model | Daily batch sweep is core | Materialised `DailyIndent` + `IndentLine` per ward per day, generated by a 06:00 job. |
| Drug model | Real catalog with FKs | `Prescription.drugId` and `InventoryItem.drugId` both reference `Drug`. Exact stock deduction and billing. |
| Frontend scope | Full rewire | Every page hits the API. Markup preserved; data sources replaced. |

## 3. Architecture

### Repo layout

```
pharmassist-ai/
├── pnpm-workspace.yaml          # new: packages/*, frontend, backend
├── packages/shared/             # new
│   ├── src/domain.ts            # Patient, Prescription, Ward, Drug, ...
│   ├── src/schemas.ts           # Zod request/response contracts
│   └── src/frequency.ts         # OD|BD|TDS|QDS|ON -> dosesPerDay
├── backend/                     # new
│   ├── prisma/schema.prisma
│   ├── prisma/seed.ts           # values lifted from frontend/src/data.ts
│   └── src/
│       ├── server.ts            # Fastify bootstrap
│       ├── plugins/{auth,prisma,errors}.ts
│       ├── modules/
│       │   ├── auth/  patients/  prescriptions/
│       │   ├── wards/ indents/   inventory/  billing/  activity/
│       └── jobs/sweep.ts        # 06:00 daily indent generation
└── frontend/                    # existing, rewired
    └── src/api/                 # new: client + TanStack Query hooks
```

### Module convention

Each `modules/<name>/` contains exactly three files:

- `routes.ts` — HTTP concerns and Zod validation only. No business logic.
- `service.ts` — business rules. The only layer permitted to touch Prisma.
- `service.test.ts` — tests against the service, not the HTTP surface.

This boundary is what lets the cron job and the REST endpoint share one sweep implementation rather than drifting into two.

### Layering rule

`shared` depends on nothing. `backend` depends on `shared`. `frontend` depends on `shared`. Backend and frontend never import each other.

`packages/shared` is the contract. `frontend/src/types.ts` becomes a re-export of it, so existing page imports keep working unchanged while the definitions move to one place.

## 4. Data model

Eleven tables. All money is `Decimal(10,2)` — never float. Currency is GHS, a constant, not a column.

### Identity & structure

- **`User`** — `username` (unique), `passwordHash` (argon2id), `displayName`, `role` (`pharmacist|nurse|doctor`), `wardId?`.
- **`Ward`** — `code` (`'Ward 4A'`), `name` (`'General Medicine'`). The UI's display string is composed as `${code} — ${name}` at the DTO boundary, retiring the `.split(' — ')` hack.
- **`Patient`** — `mrn` (unique), `name`, `dateOfBirth`, `gender`, `phone`, `wardId` FK, `bed`, `admissionDate`, `diagnosis`, `allergies`, `status` (`admitted|discharged`).

### Catalog & stock

- **`Drug`** — `name`, `strength`, `form`, `category`, `unitPrice`, and `label` (`'Furosemide 40mg'`) so existing seed strings map 1:1.
- **`InventoryItem`** — `drugId` (unique), `currentStock`, `reorderLevel`.
- **`StockMovement`** — `drugId`, `delta`, `reason` (`dispense|restock|adjustment`), `ref`, `actorId`. Append-only audit trail; `currentStock` is the maintained running total.

### Clinical

- **`Prescription`** — `patientId`, `drugId` FK, `dose`, `route`, `frequency`, `foodTiming`, `timeOfDay[]`, `startDate`, `durationDays`, `status` (`active|stopped|completed`), `stopReason`, `notes`, `prescribedById`, `stoppedById`, `stoppedAt`.

### The indent loop

- **`DailyIndent`** — `wardId`, `indentDate`, `status` (`pending|swept|dispensed`), `generatedAt`. **Unique on `(wardId, indentDate)`** — this constraint is what makes the sweep idempotent.
- **`IndentLine`** — `indentId`, `patientId`, `prescriptionId`, `drugId`, `qty`, `treatmentDay`, `status` (`pending|dispensed|cancelled`), `dispensedById`, `dispensedAt`.
- **`BillingLine`** — `indentLineId` (unique), `patientId`, `wardId`, `drugId`, `qty`, `unitPrice`, `total`, `status` (`pending|billed|voided`), `billedById`, `billedAt`, `createdAt`. This is the UI's `Transaction`: its `timestamp` maps to `createdAt` (dispense time), and its `batchId` is derived from the parent `DailyIndent` rather than stored twice.
- **`ActivityEvent`** — `type` (`dispense|prescription|stop|restock|register`), optional patient/ward/drug refs, `text`, `actorId`, `occurredAt`.

### Derived, never stored

Computed in the response DTO so page markup stays untouched:

- `InventoryItem.status` — `critical` if `stock <= reorderLevel * 0.2`, `low` if `<= reorderLevel`, else `ok`. Mirrors `InventoryPage.getStatus` exactly.
- `Prescription.currentDay` — days since `startDate` + 1. Auto-`completed` once it exceeds `durationDays`.
- `Ward.sweepStatus` / `Ward.activePatients` — from today's `DailyIndent` and the admitted-patient count.

### Daily quantity

`qty = dosesPerDay(frequency)`, where `OD:1, BD:2, TDS:3, QDS:4, ON:1`. Defined once in `packages/shared/src/frequency.ts` so the sweep job and the UI agree by construction.

### Seed data

4 wards, 5 patients, 15 drugs, 12 inventory rows — all lifted from `frontend/src/data.ts`. Unit prices come from the existing `TRANSACTIONS` rows (Amoxicillin 0.85, Metformin 0.42, Furosemide 0.30, Atorvastatin 1.20, …). Drugs with no transaction history get prices assigned explicitly in the seed file rather than guessed at runtime.

### The invariant this model asserts

**Dispensing is the only way a billing line is created, and the only way stock moves.** No orphan transactions.

## 5. API surface

Each endpoint traced to the page that requires it.

### Auth
- `POST /api/auth/login` — returns the user with role and ward from the DB record.
- `GET /api/auth/me`
- `POST /api/auth/logout`

`LoginPage` loses its role picker and ward dropdown; both become display-only after sign-in.

### Wards
- `GET /api/wards` — includes derived `sweepStatus` and `activePatients`. Feeds `DashboardPage` and `WardSweepPage` tabs.

### Patients
- `GET /api/patients?wardId=&search=`
- `GET /api/patients/:id`
- `POST /api/patients`

Replaces `INITIAL_PATIENTS` and `registerPatient`.

### Prescriptions
- `POST /api/patients/:id/prescriptions`
- `PATCH /api/prescriptions/:id`
- `POST /api/prescriptions/:id/stop`

Replaces `addPrescription` / `editPrescription` / `stopPrescription` in `App.tsx`.

### Indents
- `POST /api/indents/sweep` — accepts `date`, optional `wardId`, `preview: true`.
- `GET /api/wards/:id/pickup-list?date=` — returns exactly the shape `buildPatientPickList` builds today, so `WardSweepPage` markup is untouched.
- `POST /api/indents/dispense`

### Inventory
- `GET /api/inventory?category=&search=`
- `POST /api/inventory/:drugId/restock`

### Billing
- `GET /api/billing?wardId=&date=` — pre-grouped by patient.
- `POST /api/billing/confirm`

### Activity
- `GET /api/activity?type=&date=&limit=`

### No `/api/dashboard`

`DashboardPage`'s four metric tiles each drill down into a full list, so the page composes the endpoints above. One source of truth per number, and the drill-down data is already loaded.

## 6. Critical flows

### Dispense — single Prisma `$transaction`, all-or-nothing

`POST /api/indents/dispense { patientId, wardId, date }`

1. Load that patient's `pending` indent lines. None → `404`. Already dispensed → `409 BATCH_ALREADY_FULFILLED`.
2. Check stock for **every** line before writing any. Short on one → `409 INSUFFICIENT_STOCK`; nothing commits.
3. Decrement `InventoryItem.currentStock`; append `StockMovement(reason: dispense)`.
4. Mark lines `dispensed` with `dispensedById` / `dispensedAt`.
5. Create one `BillingLine` per line, `status: pending`, with `unitPrice` **snapshotted from the catalog at dispense time**. Later catalog price changes must not rewrite billed history.
6. Append `ActivityEvent(type: dispense)`.
7. If every line in the ward's indent is now dispensed, set `DailyIndent.status = dispensed`.

### Sweep job

`node-cron` at 06:00 server time calls the same service as `POST /api/indents/sweep` — one code path, so the endpoint is a genuine manual re-trigger rather than a parallel implementation.

- Idempotent via `unique(wardId, indentDate)`. A re-run adds only missing lines, never duplicates.
- Includes prescriptions where `status = active` and `startDate <= date < startDate + durationDays`.
- Skips stopped and completed prescriptions.
- `preview: true` computes and returns without writing.

### Stop order

`POST /api/prescriptions/:id/stop { reason }`

Sets the prescription to `stopped` with a reason, then cancels **pending** indent lines for today and forward. Already-dispensed lines are never touched — the patient received the drug and owes for it.

### Billing confirm

`POST /api/billing/confirm { patientId, date }`

Marks that patient's `pending` billing lines for the date as `billed`. Confirming an already-billed group → `409 ALREADY_BILLED`.

### Restock

`POST /api/inventory/:drugId/restock { qty, ref }`

Increments `currentStock`, appends `StockMovement(reason: restock)` and `ActivityEvent(type: restock)`.

## 7. Auth & RBAC

JWT carried in an **httpOnly, `SameSite=Lax` cookie** — not `localStorage`. This is patient data, and `localStorage` is readable by any injected script. Vite dev-proxies `/api` to the backend so both sides are same-origin; no CORS configuration and no CSRF token are required.

Role guards are enforced server-side, per route:

| Role | Permissions |
|---|---|
| Doctor | Create, edit, and stop prescriptions. Read patients. |
| Pharmacist | Dispense, restock, confirm billing. Full read. |
| Nurse | Read only, scoped to their own `wardId`. |

The nurse ward-scoping currently done client-side in `DashboardPage` becomes a server-side filter.

---

## 8. Errors

Single envelope: `{ success: false, error: CODE, message }`.

| Code | HTTP | Meaning |
|---|---|---|
| `INVALID_INPUT` | 400 | Zod validation failure. |
| `AUTH_EXPIRED` | 401 | Missing or expired token. |
| `FORBIDDEN` | 403 | Role or ward scope denies the action. |
| `RX_NOT_FOUND` | 404 | Prescription does not exist. |
| `BATCH_ALREADY_FULFILLED` | 409 | Duplicate dispense attempt. |
| `INSUFFICIENT_STOCK` | 409 | Not enough stock to fulfil the batch. |
| `ALREADY_BILLED` | 409 | Duplicate billing confirmation. |
| `DATABASE_ERROR` | 500 | Internal fault. |

## 9. Frontend rewire

Add TanStack Query plus a provider in `main.tsx`. New `src/api/`:

- `client.ts` — fetch wrapper with `credentials: 'include'`, unwraps the error envelope.
- Per-domain hook files: `useWards`, `usePatients`, `useDispense`, and so on.

Vite dev-proxies `/api` to the backend. `src/types.ts` becomes a re-export of `@pharmassist/shared`. `src/data.ts` is deleted; its contents now live in `backend/prisma/seed.ts`.

`App.tsx` sheds the `patients` state and all four mutation handlers, since pages fetch their own data. What remains is routing plus auth state from `GET /api/auth/me`.

### Local state: what stays, what goes

Not all local state is fake, and the distinction matters:

- **Stays local** — the `'confirming'` step in `WardSweepPage` and `BillingPage`. This is genuine UI state; routing it through the server would make cancelling a confirm dialog require a round trip.
- **Becomes server-derived** — `'dispensed'` and `'billed'`.
- **Disappears entirely** — `InventoryPage`'s `stocks` override map.

### Loading and error states

Pages currently have none. Rather than add a spinner dependency, each page early-returns using the muted-text empty-state styling `WardSweepPage` already uses (`"No active prescriptions for this ward today."`), keeping the visual language consistent.

## 10. Testing

Vitest, service-level, against a real Postgres test database. Priority targets:

1. Frequency math (`dosesPerDay` across all five codes).
2. Sweep idempotency — running twice produces no duplicate lines.
3. Dispense atomicity — insufficient stock on line 3 of 4 rolls back lines 1 and 2.
4. Stop-order cancellation boundaries — pending lines cancelled, dispensed lines untouched.
5. Billing state machine — pending → billed, and the duplicate-confirm rejection.
6. RBAC denials — nurse cannot dispense, doctor cannot restock, nurse cannot read another ward.

## 11. Phasing

Each phase leaves the application runnable.

| # | Phase | Delivers |
|---|---|---|
| 0 | Workspace | pnpm workspace, `packages/shared`, `types.ts` re-export. Frontend still on mocks, build green. |
| 1 | Backend skeleton | Fastify, Prisma schema, first migration, seed, healthcheck. No domain routes. |
| 2 | Auth | argon2 users, JWT cookie, role guards, `/me`. `LoginPage` wired — first real end-to-end path. |
| 3 | Read path | Wards / patients / inventory / activity endpoints; wires Dashboard, Patients, PatientDetail, Inventory, RecentActivity, DoctorPatients. |
| 4 | **The loop** | Sweep job, pickup list, dispense, billing; wires WardSweep and Billing. Highest risk, heaviest tests. |
| 5 | Writes | Register patient, prescribe/edit/stop, restock; wires the remaining forms. |
| 6 | Docs | Rewrite `API_ENDPOINTS_DETAILED.md` and `INPATIENT_AUTO_INDENT_MODULE_SPEC.md` from the shipped code. |

Phase 4 is where the real risk sits — the only phase touching money, stock, and atomicity together. Phases 0–3 exist largely to make Phase 4 boring.

## 12. Out of scope (YAGNI)

- Discharge workflow
- Bill voiding and refunds
- Refresh-token rotation
- Pagination beyond a `limit` parameter
- Multi-hospital tenancy
- Importing the 11 MB `Medicine_Names.csv`
- Anything from `demo/` — whiteboard, OCR, medicine matching
- `healthy-hands-app-main/` remains untouched
